프론트엔드 테스트의 필요성 자체는 이제 크게 설명하지 않아도 될 만큼 잘 알려져 있다.  
버그를 줄이고, 리팩토링을 안전하게 만들고, 협업 과정에서 변경 영향도를 빠르게 확인할 수 있다는 점은 누구나 공감하는 이야기다.

문제는 실무에서 늘 이상적으로 움직일 수는 없다는 데 있다.  
특히 SI 프로젝트처럼 일정과 비용이 명확하게 제한된 환경에서는 테스트를 “잘 도입하는 것”보다 먼저, **어디까지 테스트할 것인지 정하는 일**이 더 중요했다.

나 역시 처음에는 테스트가 있으면 좋다는 생각으로 접근했지만, 막상 프로젝트를 진행하다 보니 모든 화면과 기능을 촘촘하게 검증하는 방식은 현실적이지 않았다.  
요구사항은 자주 바뀌고, 화면 구조도 계속 수정되며, 테스트 코드 자체를 관리하는 비용도 무시하기 어려웠다.

그래서 이번 글에서는 Vitest/Jest와 React Testing Library를 도입하면서,  
**한정된 리소스 안에서 어떤 기준으로 테스트 범위를 정했는지**, 그리고 실제로 적용해보며 느낀 장단점을 정리해보려고 한다.

## 관련 개념 정리

### 왜 프론트엔드 테스트가 필요한가

프론트엔드 테스트는 단순히 “테스트를 많이 작성했다”는 기록을 남기기 위한 작업이 아니다.  
실제로는 다음과 같은 이유 때문에 팀 생산성과 유지보수성에 직접적인 영향을 준다.

- 공통 컴포넌트 수정 시 회귀 버그를 빠르게 확인할 수 있다
- 리팩토링할 때 기존 동작이 깨지지 않았는지 검증할 수 있다
- 기능의 기대 동작이 테스트 코드로 남아 일종의 문서 역할을 한다
- QA 단계 이전에 기본적인 문제를 선제적으로 걸러낼 수 있다

특히 여러 사람이 동시에 작업하거나, 이후 유지보수 담당자가 바뀌는 환경에서는 테스트 유무가 체감 차이를 크게 만든다.  
코드를 처음 보는 사람도 테스트를 통해 “이 컴포넌트는 어떤 동작을 보장해야 하는지”를 빠르게 파악할 수 있기 때문이다.

### Vitest/Jest와 React Testing Library의 역할

이번 프로젝트에서 고려한 조합은 `Vitest/Jest + React Testing Library`였다.

먼저 Vitest와 Jest는 테스트를 실행하고, assertion을 작성하고, mocking을 처리하는 **테스트 러너이자 실행 환경**에 가깝다.  
즉, 테스트를 돌아가게 만드는 기반 도구라고 보는 편이 이해하기 쉽다.

React Testing Library는 조금 결이 다르다.  
이 도구는 컴포넌트 내부 구현을 직접 검증하기보다, **사용자 관점에서 화면이 어떻게 보이고 동작하는지**를 테스트하는 데 초점이 있다.

예를 들어 다음처럼 접근한다.

- 특정 버튼이 화면에 보이는가
- 사용자가 입력창에 값을 입력할 수 있는가
- 버튼 클릭 후 기대한 문구가 나타나는가
- 조건에 따라 안내 메시지가 다르게 렌더링되는가

이 방식이 중요한 이유는, 테스트가 컴포넌트 내부 구조에 과하게 묶이지 않도록 도와주기 때문이다.  
테스트가 구현 디테일에 너무 강하게 결합되면, 기능은 그대로인데 코드 구조만 바뀌어도 테스트가 쉽게 깨진다.  
반면 사용자 기준의 검증은 상대적으로 유지보수성이 더 좋다.

### 왜 모든 것을 테스트하지 않았는가

이론적으로는 테스트 범위가 넓을수록 좋다.  
하지만 SI 프로젝트에서는 이 원칙을 그대로 적용하기 어려웠다.

주요 이유는 명확했다.

- 일정이 촉박했다
- 예산이 한정적이었다
- 요구사항 변경 빈도가 높았다
- 화면 구조가 자주 바뀌는 구간이 많았다
- 테스트 코드 유지 비용도 결국 개발 비용에 포함됐다

테스트는 공짜가 아니다.  
코드를 작성하는 시간뿐 아니라 요구사항 변경에 맞춰 테스트를 수정하고 관리하는 시간까지 고려해야 했다.

그래서 이번 프로젝트에서는 “테스트를 많이 작성하자”보다,  
**적은 비용으로 가장 큰 효과를 낼 수 있는 지점을 먼저 검증하자**는 기준으로 접근했다.

### 테스트 대상 선정 기준

실제로는 아래 기준을 중심으로 테스트 대상을 추렸다.

| 구분                           | 테스트 여부        | 이유                                             |
| ------------------------------ | ------------------ | ------------------------------------------------ |
| 공통 버튼/입력/모달 컴포넌트   | 적극 적용          | 재사용 빈도가 높고 한 번 깨지면 영향 범위가 넓다 |
| 조건 분기가 많은 폼 로직       | 적용               | 예외 케이스가 많아 수동 검증만으로 놓치기 쉽다   |
| 핵심 사용자 흐름에 포함된 기능 | 선택 적용          | 장애 발생 시 업무 영향도가 크다                  |
| 단순 정적 UI                   | 최소화             | 테스트 대비 유지 비용이 더 크다                  |
| 자주 바뀌는 화면 레이아웃      | 최소화 또는 후순위 | 마크업 변경만으로 테스트가 자주 깨질 수 있다     |

결국 기준은 두 가지였다.

첫 번째는 **영향도**다.  
깨졌을 때 문제 범위가 큰 기능인가.

두 번째는 **변경 비용 대비 효과**다.  
테스트를 써두면 반복적으로 이득을 보는 영역인가.

이 기준을 두고 보니, 모든 컴포넌트를 동일하게 다루는 방식보다는  
공통 컴포넌트, 핵심 비즈니스 로직, 복잡한 입력/검증 흐름에 집중하는 편이 훨씬 현실적이었다.

## 실제 적용

### 적용 전

초기 상태는 흔히 볼 수 있는 수동 검증 중심의 운영 방식에 가까웠다.  
기능을 구현한 뒤 직접 화면에서 눌러보고, QA 단계에서 다시 확인하는 흐름이었다.

이 방식은 개발 초반에는 빠르게 느껴질 수 있다.  
문제는 프로젝트가 커질수록, 그리고 공통 컴포넌트가 늘어날수록 작은 수정이 예상치 못한 사이드 이펙트를 만드는 경우가 많아진다는 점이다.

예를 들어 공통 버튼 컴포넌트의 disabled 처리나 폼 검증 메시지 조건을 수정했을 때,  
현재 작업 중인 화면은 괜찮아 보여도 다른 화면에서 미묘하게 깨지는 일이 생겼다.  
이런 문제는 보통 “개발자는 지나쳤고, QA에서 뒤늦게 발견하는” 형태로 나타났다.

### 적용 방법

프로젝트 환경에 따라 도구 선택 기준은 조금 달라질 수 있다.

- Vite 기반 프로젝트라면 `Vitest`가 설정과 실행 속도 측면에서 자연스럽다
- 기존 팀이 Jest에 익숙하고 관련 설정이 이미 있다면 `Jest`를 유지하는 것도 합리적이다
- 컴포넌트 동작 검증은 `React Testing Library`를 중심으로 가져간다

이번에 중요했던 건 특정 도구를 선택한 이유보다,  
**테스트 범위를 어떻게 제한하고 운영했는가**였다.

적용 원칙은 대략 다음과 같았다.

- 공통 컴포넌트는 우선 테스트한다
- 복잡한 폼 검증 로직은 테스트한다
- 핵심 사용자 흐름 중 오류 비용이 큰 부분은 테스트한다
- 단순 렌더링 위주의 UI는 과감히 제외한다
- snapshot 테스트는 최소화한다
- 내부 구현보다 사용자 동작 기준으로 검증한다
- mocking은 꼭 필요한 경우에만 사용한다

이 원칙을 정해두니 “이것도 테스트해야 하나?”라는 고민에 드는 시간이 줄었다.  
무엇보다 팀 내에서도 테스트 작성 기준을 어느 정도 공유할 수 있었다.

### 예시 1. 공통 버튼 컴포넌트 테스트

공통 버튼은 여러 화면에서 재사용되기 때문에 작은 변경도 영향 범위가 넓다.  
그래서 가장 먼저 테스트하기 좋은 대상이었다.

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { Button } from "./Button";

test("버튼 클릭 시 onClick이 호출된다", async () => {
  const user = userEvent.setup();
  const handleClick = vi.fn();

  render(<Button onClick={handleClick}>저장</Button>);

  await user.click(screen.getByRole("button", { name: "저장" }));

  expect(handleClick).toHaveBeenCalledTimes(1);
});

test("disabled 상태에서는 클릭되지 않는다", async () => {
  const user = userEvent.setup();
  const handleClick = vi.fn();

  render(
    <Button disabled onClick={handleClick}>
      저장
    </Button>
  );

  await user.click(screen.getByRole("button", { name: "저장" }));

  expect(handleClick).not.toHaveBeenCalled();
});
```

이런 테스트는 작성 비용이 크지 않으면서도,  
공통 컴포넌트의 기본 동작을 안정적으로 보장해준다는 장점이 있었다.

### 예시 2. 폼 검증 테스트

폼 검증은 조건 분기가 많고, 실수해도 바로 장애로 이어질 수 있어 테스트 우선순위가 높았다.

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./LoginForm";

test("이메일과 비밀번호를 입력하지 않으면 검증 메시지가 노출된다", async () => {
  const user = userEvent.setup();

  render(<LoginForm />);

  await user.click(screen.getByRole("button", { name: "로그인" }));

  expect(screen.getByText("이메일을 입력해주세요.")).toBeInTheDocument();
  expect(screen.getByText("비밀번호를 입력해주세요.")).toBeInTheDocument();
});

test("올바른 값을 입력하면 로그인 요청을 진행한다", async () => {
  const user = userEvent.setup();

  render(<LoginForm />);

  await user.type(screen.getByLabelText("이메일"), "test@test.com");
  await user.type(screen.getByLabelText("비밀번호"), "12345678");
  await user.click(screen.getByRole("button", { name: "로그인" }));

  expect(screen.getByText("로그인 요청 중입니다.")).toBeInTheDocument();
});
```

이런 테스트는 QA 단계에서 자주 반복하던 검증을 자동화하는 데 도움이 됐다.  
특히 요구사항 변경으로 검증 메시지나 제출 조건이 바뀌었을 때 빠르게 확인할 수 있었다.

### 예시 3. 유틸 함수 테스트

UI보다 더 안정적으로 테스트하기 좋은 영역은 유틸 함수나 순수 함수 로직이다.  
입력과 출력이 명확해 테스트 유지 비용이 낮고, 실수도 빠르게 잡을 수 있다.

```ts
import { formatPhoneNumber } from "./formatPhoneNumber";

test("휴대폰 번호를 하이픈 형식으로 변환한다", () => {
  expect(formatPhoneNumber("01012345678")).toBe("010-1234-5678");
});

test("빈 값이 들어오면 빈 문자열을 반환한다", () => {
  expect(formatPhoneNumber("")).toBe("");
});
```

실제로 이런 테스트는 작성 부담이 적고,  
로직 변경으로 인한 회귀를 막는 효과가 커서 비용 대비 만족도가 높았다.

### 적용 후

모든 것이 극적으로 바뀌었다고 말하기는 어렵다.  
하지만 분명한 변화는 있었다.

먼저 공통 컴포넌트를 수정할 때 심리적 부담이 줄었다.  
버튼, 입력, 모달처럼 자주 쓰이는 요소는 최소한의 안전망이 생겼기 때문이다.

또한 핵심 로직을 수정할 때 “직접 눌러보며 확인”하는 시간도 조금씩 줄어들었다.  
물론 최종적으로는 여전히 사람이 확인해야 하는 부분이 있었지만,  
적어도 기본적인 회귀 이슈를 초기에 걸러낼 수 있었다.

반대로 테스트를 도입했다고 해서 모든 문제가 해결되지는 않았다.  
화면 구조가 자주 바뀌는 구간에서는 테스트 코드 수정 비용이 계속 발생했고,  
작성 기준이 불분명한 테스트는 오히려 관리 포인트만 늘어났다.

결국 테스트는 도입 자체보다 **범위를 잘 정하는 것**이 훨씬 중요했다.

## 적용 후기

### 좋았던 점

가장 좋았던 점은 **공통 영역의 신뢰도가 올라갔다는 것**이다.  
재사용되는 컴포넌트와 반복되는 검증 로직에 테스트가 붙어 있으니, 작은 수정에도 조금 더 자신 있게 대응할 수 있었다.

또 하나는 **리팩토링에 대한 심리적 안정감**이었다.  
기존에는 “이거 수정하면 다른 데서 문제 나는 거 아닐까?”라는 불안이 컸는데,  
적어도 핵심 동작에 대한 테스트가 있으면 변경을 시도하기가 쉬웠다.

협업 측면에서도 장점이 있었다.  
테스트 코드는 단순한 검증 코드가 아니라, 이 컴포넌트가 어떤 동작을 해야 하는지 설명하는 문서 역할도 했다.  
신규 투입 인원이 로직을 이해하는 데 꽤 도움이 됐다.

### 아쉬웠던 점

반대로 아쉬운 점도 분명했다.

가장 큰 문제는 **유지보수 비용**이었다.  
요구사항 변경이 잦은 화면은 UI 구조가 조금만 달라져도 테스트를 수정해야 했다.  
특히 세부 DOM 구조에 민감한 테스트는 금방 피로도가 높아졌다.

또 일정이 빠듯한 상황에서는 테스트 코드 작성 자체가 부담으로 느껴질 때도 있었다.  
실제로 기능 구현, 버그 수정, QA 대응이 동시에 몰리는 시점에는  
테스트를 정교하게 작성하는 시간이 쉽게 확보되지 않았다.

팀 차원의 숙련도 차이도 있었다.  
누군가는 사용자 중심 테스트를 잘 작성했지만, 누군가는 내부 구현에 과하게 의존하는 테스트를 작성해 유지보수성을 떨어뜨리기도 했다.  
결국 도구보다도 팀 내 작성 기준을 맞추는 일이 꽤 중요했다.

### 그래서 어떤 전략이 현실적이었는가

이번 경험을 통해 가장 크게 느낀 건,  
SI 프로젝트에서 테스트는 “많이 하는 것”보다 **효율적으로 하는 것**이 더 중요하다는 점이다.

현실적으로 모든 화면과 인터랙션을 다 검증하는 것은 어렵다.  
오히려 그렇게 접근하면 테스트 코드 유지 자체가 또 다른 비용이 된다.

그래서 아래처럼 정리하는 방식이 가장 현실적이었다.

- 공통 컴포넌트는 우선 테스트한다
- 장애 영향도가 큰 핵심 기능을 테스트한다
- 조건 분기가 많은 로직을 테스트한다
- 단순하고 자주 바뀌는 UI는 과감히 후순위로 둔다
- 테스트 도입 목표를 “완전한 커버리지”가 아니라 “핵심 회귀 방지”에 둔다

결국 중요한 건 테스트 도구를 썼다는 사실이 아니라,  
**어떤 기준으로 테스트 범위를 정하고 팀이 그 기준을 꾸준히 유지할 수 있느냐**였다.

### 추천하는 상황

아래와 같은 상황이라면 이 방식이 특히 잘 맞는다고 느꼈다.

- 공통 컴포넌트 비중이 높은 프로젝트
- 유지보수나 인수인계 가능성이 높은 프로젝트
- QA만으로 회귀 이슈를 모두 잡기 어려운 프로젝트
- 핵심 비즈니스 로직의 안정성이 중요한 프로젝트

반대로 초기 요구사항이 매우 유동적이고, 화면 구조가 계속 바뀌는 단계라면  
처음부터 넓게 가져가기보다 범위를 좁게 시작하는 편이 더 낫다.  
그 시점에는 테스트 수를 늘리는 것보다, “어떤 영역은 반드시 보호해야 하는가”를 먼저 정하는 것이 효과적이었다.

## 마무리

Vitest/Jest와 React Testing Library는 분명 좋은 도구다.  
하지만 실제 프로젝트에서 더 중요했던 건 도구 자체보다, **한정된 일정과 비용 안에서 테스트를 어디까지 적용할지 판단하는 기준**이었다.

이번 프로젝트에서는 모든 것을 테스트하지 않았다.  
대신 공통 컴포넌트, 핵심 로직, 장애 영향도가 큰 기능처럼 비용 대비 효과가 높은 영역에 먼저 집중했다.  
그 결과 완벽하지는 않아도, 적은 비용으로 꽤 실용적인 안정성을 확보할 수 있었다.

프론트엔드 테스트는 많이 작성하는 것이 목표가 아니라,  
**가장 위험한 곳을 가장 현실적인 비용으로 먼저 보호하는 것**이 더 중요하다고 생각한다.
