React로 구성된 프로젝트 고도화 작업을 진행하면서 중복되는 UI가 많다는 것을 발견하였다.

기존 프로젝트는 페이지 단위로 컴포넌트를 관리하여 화면이 늘어날수록 비슷한 UI가 여러 파일에 흩어지고 수정 포인트가 계속 증가하는 문제였다.

프로젝트 일정이 딜레이되면서 구조를 정리할 수 있는 시간이 생겨 기존의 "화면별 구현" 방식에서 벗어나 "UI 컴포넌트 재활용" 중심으로 전환하기 위한 리팩토링을 진행했다.

리팩토링은 Atomic Design을 기반으로 디자이너와 협업하여 컴포넌트를 재정리하는 방식으로 시작했다.  
다만 프로젝트 특성에 맞게 일부 분류 기준은 유연하게 수정해 적용하였고 Figma를 공통 기준점으로 삼아 협업 규칙도 함께 정리했다.

## 관련 개념 정리

### Atomic Design이 중요한 이유

Atomic Design은 UI를 작은 단위부터 큰 단위로 조합해 설계하는 방식이다.

- `Atom`: 버튼, 아이콘, 텍스트처럼 더 쪼개기 어려운 최소 단위
- `Molecule`: 검색 입력창 + 버튼처럼 Atom의 조합
- `Organism`: 헤더, 카드 리스트처럼 Molecule/Atom의 큰 조합
- `Template`: 페이지 레이아웃 구조
- `Page`: 실제 데이터가 들어간 최종 화면

이 구조의 장점은 "재사용 가능한 최소 단위"를 먼저 고정하고, 그 위에 조합을 쌓아가며 일관성을 유지할 수 있다는 점이다.

다만 이번 프로젝트에서는 이 구조를 그대로 복제하지 않고 운영 방식에 맞게 조정했다.  
예를 들어 `Template`과 `Page`를 엄격히 분리하기보다, 라우팅/데이터 의존이 강한 화면은 `Page`에서 직접 레이아웃을 소유하도록 두고, 반복 레이아웃만 `Template`로 올렸다.

### React 프로젝트에서의 협업 기준

React에서는 컴포넌트 재사용이 쉬운 만큼, 기준 없이 만들면 유사 컴포넌트가 빠르게 늘어난다.  
그래서 개발/디자인 모두 같은 기준점을 가져야 한다.

이번에는 다음 3가지를 공통 기준으로 잡았다.

- **역할 기준**: 이 컴포넌트가 표현 전용인지, 조합 단위인지, 화면 단위인지
- **변경 빈도 기준**: 자주 바뀌는 영역은 상위 조합에서 처리하고, 하위 단위는 안정적으로 유지
- **재사용 범위 기준**: 한 화면 전용인지, 여러 화면에서 공통으로 쓰일지

### Figma를 기준점으로 맞춘 이유

이전에는 시안을 보고 개발자가 임의로 컴포넌트 경계를 나누는 경우가 많았다.  
이번에는 Figma 컴포넌트/Variants 구조를 먼저 확인하고, React 컴포넌트 구조를 그에 최대한 1:1로 맞췄다.

예를 들어 Figma에서 버튼이 `Primary/Secondary` Variant로 관리되면, 코드에서도 단일 `Button` 컴포넌트와 `variant` prop으로 대응했다.  
이 방식 덕분에 디자이너와 개발자가 같은 단어로 UI를 설명할 수 있게 됐다.

## 실제 적용

### 적용 전

- 화면 단위로 컴포넌트가 만들어져 중복 UI가 많았음
- 버튼/태그/입력창이 비슷하지만 서로 다른 구현으로 존재했음
- Figma 수정사항이 생기면 여러 파일을 수동으로 찾아 수정했음

### 적용 방법

먼저 Figma를 기준으로 공통 UI를 추출하고 Atomic Design 단계로 분류했다.  
이때 "규칙을 그대로 적용"하기보다 프로젝트의 개발 속도와 팀 이해도를 고려해 분류 단계를 단순화했다.

```tsx
// 예시: 공통 Atom Button
type ButtonProps = {
  variant?: "primary" | "secondary";
  size?: "sm" | "md" | "lg";
  disabled?: boolean;
  onClick?: () => void;
  children: React.ReactNode;
};

export function Button({
  variant = "primary",
  size = "md",
  disabled = false,
  onClick,
  children,
}: ButtonProps) {
  return (
    <button
      data-variant={variant}
      data-size={size}
      disabled={disabled}
      onClick={onClick}
    >
      {children}
    </button>
  );
}
```

"기준점을 어떤 식으로 나눴는지"를 저장소 내에서 문서화하였고  
핵심은 분류의 정교함보다 **중복 UI를 줄이고 재사용률을 높이는 것**이었다.

| 구분 기준        | 판단 질문                         | 배치 단계 |
| ---------------- | --------------------------------- | --------- |
| UI 최소 단위     | 더 쪼개면 의미가 사라지는가?      | Atom      |
| 기능 조합 단위   | 2개 이상의 Atom을 조합하는가?     | Molecule  |
| 화면 구획 단위   | 독립된 섹션으로 재사용 가능한가?  | Organism  |
| 레이아웃 단위    | 데이터 없이 구조만 설명 가능한가? | Template  |
| 실제 라우트 단위 | API/상태가 결합된 최종 화면인가?  | Page      |

폴더 구조도 같은 기준으로 정리했다.

```text
src/components
  /atoms
  /molecules
  /organisms
  /templates
src/pages
```

### 적용 후

- 공통 컴포넌트 수정 시 반영 범위가 명확해져 유지보수 시간이 줄었음
- 디자이너와의 커뮤니케이션에서 "Figma 컴포넌트 이름 = React 컴포넌트 이름"으로 정렬됨
- 신규 화면 개발 시 기존 Molecule/Organism을 조합하는 방식으로 속도가 안정화됨

## 적용 후기

Atomic Design 자체가 정답은 아니지만, 기준점 없이 커지는 UI를 정리하는 데는 확실히 효과가 있었다.  
특히 React + Figma 협업 환경에서는 "컴포넌트 경계를 어디서 나눌지"를 먼저 합의하는 것만으로도 개발과 협업의 마찰을 크게 줄일 수 있었다.
다만 프로젝트 규모가 더 커질수록 Atomic Design만으로는 도메인 경계나 상태 흐름까지 설명하기 어려운 한계도 느꼈다.  
결국 컴포넌트 분류 기준뿐 아니라 기능 단위 아키텍처와 상태 관리 전략을 함께 가져가야 구조가 안정적으로 유지된다는 점을 배웠다.

### 좋았던 점

- 컴포넌트 재사용 범위가 명확해져 중복 구현이 크게 줄었다.
- 디자이너와 협업할 때 논의 단위가 컴포넌트 기준으로 정리되어 의사결정이 빨라졌다.
- Figma 변경사항을 코드로 옮길 때 영향 범위를 예측하기 쉬워졌다.

### 아쉬웠던 점

- 초기 분류 작업(Atom/Molecule/Organism)은 생각보다 시간이 많이 들었다.
- 팀원마다 "어디까지 Atom인가"에 대한 해석이 달라 초반 합의 과정이 필요했다.
